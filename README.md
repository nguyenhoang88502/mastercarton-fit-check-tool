# WVN Master Carton Fit Tool — Maintainer Notes

This repository contains an offline browser tool for checking whether a finished-good package can fit into an existing master carton and, when none fits, proposing practical new carton dimensions.

The notes below are intended to give a future maintainer or coding model enough context to continue safely without reverse-engineering the whole HTML file.

## Files

- `WVN_Master_Carton_Fit_Tool.html` — the complete application. HTML, CSS, JavaScript, XLSX parsing, packing logic, localization, and the SVG 3D visualizer are embedded in this one file.
- `Open_WVN_Master_Carton_Fit_Tool.cmd` — the supported launcher.
- `carton_tool_input.xlsx` — the current source workbook.
- `WVN Master Carton Workbook Manifest.json` — generated by the launcher at runtime. It lists eligible `.xlsx` files in newest-first order.
- `Weekly BOM Manifest.json` — generated by the launcher at runtime. It points to Weekly BOM files without copying them into the tool folder.

No Node.js, Python, server, database, Internet connection, or external JavaScript library is required at runtime.

## How the launcher works

Always launch the tool with `Open_WVN_Master_Carton_Fit_Tool.cmd` when automatic workbook loading is required.

The launcher:

1. Gets its own directory from `%~dp0`.
2. Scans that directory for `.xlsx` files, excluding Excel temporary files beginning with `~$`.
3. Sorts workbooks by `LastWriteTimeUtc`, newest first.
4. Writes `WVN Master Carton Workbook Manifest.json` beside the launcher.
5. Looks for the authoritative `1. Weekly BOM` directory beside the tool folder, under the user's Downloads folder, or inside the tool folder, in that order.
6. Writes `Weekly BOM Manifest.json` with absolute local `file:///` URLs, allowing a Desktop-hosted tool to read a BOM stored in Downloads when Chrome/Edge is launched with local-file access.
7. Opens the HTML in Chrome or Edge with `--allow-file-access-from-files` and an isolated temporary browser profile.

The HTML reads the first manifest entry and loads that workbook locally. If the HTML is opened directly without the launcher, the user can expose the hidden **Workbook** panel and select or drag-drop a workbook manually.

The expanded **Workbook** panel displays hyperlinks to the auto-loaded dimension workbook and Weekly BOM. These links use the same local `file:///` source addresses as the launcher manifests, allowing users to navigate to the actual source file for review or manual maintenance. Browser security does not expose the original path of a file selected through a file-input control, so manually selected files show a short explanation instead of a misleading source link.

For Weekly BOM selection, the launcher prefers a month/day embedded in filenames such as `BOM & FORMULA JUL 03 D365.xlsx`, then falls back to file modification time. This prevents a recently copied older file from replacing a newer weekly period. A manual Weekly BOM picker is available inside the collapsed **Workbook** panel.

## Current workbook schema

Sheet detection is header-based rather than dependent on exact sheet names. This allows renamed sheets such as `Dimension`, `Dimension_FG_packaging`, `Carton_Master_Verified`, or `Mastercarton_Dimensions` to work when their headers are correct.

### FG packaging dimensions

Expected source headers:

- `Item number`
- `Unit`
- `Gross weight`
- `Width`
- `Depth`
- `Height`

The calculation filters this sheet strictly to rows where `Unit = EA`. CA and PL rows must never be used because they represent carton/pallet packaging rather than the individual finished-good package.

`Width`, `Depth`, and `Height` in this source sheet are centimetres. After selecting the EA row, `DataNormalizer` multiplies every dimension by 10 before storing or calculating, so all downstream packing logic receives millimetres.

Invalid EA rows with blank, text, zero, or negative dimensions are ignored. If an item has multiple valid EA rows with different dimensions, it is flagged as a conflicting source record and is not allowed into fit, audit, optimization, or 3D calculations until the source data is corrected.

### Provisional FG-to-master-carton reference

Expected source headers:

- `FG_ID`
- `FG_Name`
- `MasterCarton_ID`
- `MasterCarton_Name`
- `Carton_Per_FG`
- `FG_Per_MasterCarton`
- `FG_BOM_ID`
- `FG_Lifecycle`
- `Carton_Lifecycle`

`FG_ID` joins to `Item number`. `FG_Per_MasterCarton` becomes the default FG target quantity. This sheet is an MVP/provisional reference only; it is not the authoritative source for the current Master Carton assignment. The tool keeps its assignment values only for comparison with the Weekly BOM.

The sheet is optional. If it is absent, the app still loads EA dimensions and carton dimensions, then builds/extends the selectable FG list from the Weekly BOM. When a target quantity is unavailable, `Mastercarton_Dimensions.fg_per_carton` is used as a clearly labelled fallback when the BOM-assigned carton has a dimension record.

### Master-carton dimensions

Expected source headers:

- `carton_id`
- `carton_name`
- `fg_per_carton`
- `carton_width_cm`
- `carton_depth_cm`
- `carton_height_cm`
- `carton_volume_mm3`
- `carton_lifecycle`

Carton width, depth, and height are converted from centimetres to millimetres by multiplying by 10. The source volume is not trusted for fit decisions; the tool recalculates volume from dimensions.

### Canonical fallback schema

The loader also supports already-normalized sheets with these headers:

- FG: `fg_id`, `fg_name`, `fg_width_mm`, `fg_depth_mm`, `fg_height_mm`, `target_qty`
- Carton: `carton_id`, `carton_name`, `carton_width_mm`, `carton_depth_mm`, `carton_height_mm`, `carton_lifecycle`

IDs are normalized to JavaScript strings. The embedded XLSX reader also recognizes simple zero-padded number formats so formatted leading zeroes can be retained where possible.

### Internal unit contract

After `DataNormalizer` finishes, every `width`, `depth`, `height`, oriented dimension, remaining-space value, clearance, and rounding increment is in millimetres. Every calculated carton/FG volume is in cubic millimetres (`mm³`). Percentages and quantities are dimensionless.

- FG source `Dimension_FG_packaging`: positive `Unit = EA` dimensions in cm → multiply by 10 → mm.
- Carton source `Mastercarton_Dimensions`: `carton_*_cm` → multiply by 10 → mm.
- Canonical `*_mm` sheets: already mm → no conversion.
- Manual NPI inputs: entered directly in mm → no conversion.
- Generated-carton clearance and rounding: 5 mm.

Do not add unit conversion inside `CartonFitEngine`, `NewCartonGenerator`, scoring, audit, or the visualizer. Those components must consume normalized mm values only.

## User workflows

### FG–Master Carton data linkage check

Selecting an existing FG performs a visible data-lineage check before the general fit search. The Weekly BOM is the source of truth for FG-to-Master-Carton assignment; the local workbook is a dimension source and provisional MVP reference:

The Existing FG area includes a dedicated FG-ID search box. Typing filters the dropdown by item ID while preserving each option's data-completeness note.

1. Find the selected FG in the newest Weekly BOM and identify its Master Carton component.
2. Treat that BOM item number as the active assigned `MasterCarton_ID`.
3. Compare it with the provisional `FG_MasterCarton.MasterCarton_ID` when that sheet/value exists.
4. Find the FG's packaging dimensions by matching `FG_ID` to `Item number` in the FG packaging-dimension sheet, retaining only `Unit = EA`, then convert its centimetre dimensions to millimetres with `×10`.
5. Find the BOM-assigned carton's dimensions by matching its item number to `Mastercarton_Dimensions.carton_id`.
6. When both dimension records exist, test the BOM-assigned carton physically with all six orientations.

If the Weekly BOM contains no Master Carton item for the FG, the provisional assignment is displayed only as a rejected comparison value and is not used as the current assignment. If multiple Master Carton candidates exist, the condition is visibly marked ambiguous and the data-link status remains incomplete.

If the Weekly BOM cannot be loaded at all, the app enters an explicit provisional fallback mode instead of disabling the existing-FG workflow. It uses `FG_MasterCarton.MasterCarton_ID`, `Dimension_FG_packaging` EA dimensions, and `Mastercarton_Dimensions` as the alternative join path. A compact amber warning appears near the top of the page stating that Weekly BOM source-of-truth validation is unavailable. Dropdown records with a complete fallback chain are labelled `Complete provisional data`, remain searchable, and can be calculated and visualized. Once a valid Weekly BOM loads, authoritative reconciliation automatically replaces fallback mode and hides the warning.

The UI shows five explicit cards:

- Finished Good ID.
- Assigned Master Carton ID.
- FG packaging-dimension status and values.
- Assigned Master Carton dimension status and values.
- Assigned-carton physical fit result for the target quantity.

The overall badge says either `DATA LINK COMPLETE` or `ASSIGNMENT OR DIMENSION DATA INCOMPLETE`. Missing records are shown in red; users do not need to infer missing joins from an empty table.

Every option in the Existing FG dropdown also includes an inline completeness note. In authoritative mode, `Data complete` requires FG ID, a positive target quantity, an unambiguous Weekly BOM Master Carton assignment, EA packaging dimensions, and assigned Master Carton dimensions. While the BOM is loading or unavailable, the same checks use the provisional `FG_MasterCarton` assignment and successful records are labelled `Complete provisional data`. Incomplete options list the exact missing elements, and the selected option repeats the status in a badge beside the dropdown.

### Latest Weekly BOM cross-check

When an existing FG is selected, the tool also checks the newest Weekly BOM loaded by the launcher:

1. Finds the selected FG in the weekly workbook.
2. Reads normalized BOM exports (`FG` / `Item number`) or repeated D365 BOM blocks (`Item number`, `Product name`, `Item group`, and component tables).
3. Uses BOM level 1 when a `BOMLevel` column exists.
4. Identifies Master Carton components by exact item-number match to `Mastercarton_Dimensions`. A product-name fallback recognizes Master Carton / shipper descriptions while explicitly excluding carton labels and stickers.
5. Uses the Weekly BOM carton item as the active assignment and compares it to provisional `MasterCarton_ID` from `FG_MasterCarton`.
6. Confirms whether every BOM carton item has valid dimensions in `Mastercarton_Dimensions`.

The panel displays the Weekly BOM filename, FG row count, authoritative BOM assignment, provisional MVP assignment, BOM carton item number/name/norm, comparison result, and dimension-data status. It is hidden for manual NPI products because those products are not expected to exist in the current BOM.

The data path is displayed as:

```text
Weekly BOM (source of truth): FG → Master Carton item → Mastercarton_Dimensions: carton_id
FG_MasterCarton (optional MVP comparison): FG_ID → provisional MasterCarton_ID
Dimension_FG_packaging: Item number → FG dimensions
```

When the linkage is complete, the initial 3D view uses the assigned Master Carton, even if another carton ranks better in the general search. The existing-carton results include an `FG relationship` column that distinguishes `ASSIGNED TO THIS FG` from alternative suitable cartons. Users can still click any alternative row to visualize it.

The Existing Carton Result table always places the currently assigned BOM Master Carton in a highlighted `CURRENT BOM` row before suitable alternatives. That row remains visible when the assigned carton fails the physical target or when its dimension record is missing.

If the assigned carton exists but physically fails, the 3D view shows its best possible arrangement and the failure against the target. If its dimension record is missing, the linkage panel states that the assigned carton cannot be plotted.

The current workbook audit found 831 FG master rows, all with a Master Carton assignment. After enforcing positive `Unit = EA` dimensions, rejecting conflicting valid EA duplicates, and requiring positive assigned-carton dimensions, 436 rows have all four required data elements. There are 301 rows with missing, invalid, or conflicting EA dimensions and 173 rows whose assigned carton has missing or invalid dimensions.

### Manual NPI check

The top form accepts:

- New FG ID, optionally.
- FG length, width, and height.
- Target quantity.

When FG ID is blank, the calculation uses the temporary internal label `MANUAL-NPI`. FG name and proposed carton name are generated internally; they are not required user inputs.

This path does not require an existing FG or BOM record.

The **Check cartons** action performs a read-only calculation. The tool cannot add the FG to Excel, write a BOM, create an EDM item, or modify any engineering source data. The FG ID, dimensions, and generated proposal details exist only for the current calculation.

The header displays a compact `Analysis Mode Only` badge so users understand that results are advisory without consuming workspace height.

The NPI form is intentionally organized into three engineering blocks:

1. Product identity — optional FG ID only.
2. Finished Good Dimensions (mm) — Length, Width, and Height in one horizontal row.
3. Target quantity.

Keep the three dimension inputs grouped in L × W × H order. The layout must not allow Height to wrap into a visually unrelated row at desktop widths.

On submission:

1. The tool tests the manual FG against all loaded existing cartons.
2. If one or more cartons fit, it shows the best ten and visualizes the highest-ranked result.
3. If none fits, it creates a temporary identifier in the form `NPI-MC-YYYYMMDD-HHMMSS`, applies the entered/generated carton name, and shows both values in the proposal banner and proposal table.
4. Manual NPI proposals prioritize the selected FG's packing density and smaller carton volume, then shared compatibility with known FG codes.

The temporary ID is not a production item number. Proposal results remain labelled:

`ENGINEERING PROPOSAL — PHYSICAL SAMPLE VALIDATION REQUIRED`

### Historical BOM packaging audit

The audit panel accepts an existing Finished Good ID and any current Master Carton ID. The pair does not need to be the carton assigned to that FG in `FG_MasterCarton`, which allows legacy and unusual BOM combinations to be reviewed.

The audit resolves dimensions from the normalized workbook data and calculates:

- BOM target quantity from `FG_Per_MasterCarton`.
- Actual physical capacity using all six orthogonal orientations.
- Best arrangement and remaining space.
- BOM volumetric utilization: `(FG volume × target quantity) / carton volume`.
- Maximum packed utilization: `(FG volume × physical capacity) / carton volume`.

The default underutilization threshold is 75% and is editable from 1% to 100%. A pair is flagged when BOM utilization is below the threshold or when the target quantity does not physically fit. A physically fitting pair below the threshold is explicitly labelled `HIGH WASTE / UNDERUTILIZED` in red; it is no longer incorrectly displayed as a green simple-grid pass. Utilization exactly equal to the threshold passes the threshold check.

Flagged pairs trigger a density-first optimized-carton calculation. Current legacy statistics and the suggested solution are displayed side by side, including utilization improvement and carton-volume reduction. Separate buttons load the current or suggested arrangement into the shared 3D visualizer.

This workflow is read-only. There is no “apply,” “add,” or EDM-write action. Suggested dimensions must be validated physically and entered into Excel/EDM manually through the company's approved engineering process.

### Existing FG check

The existing-FG dropdown is populated from the joined workbook data. Selecting an FG uses its workbook dimensions and default `FG_Per_MasterCarton` target. The target can be edited before recalculation.

### Workbook controls

Excel upload controls are hidden by default. The **Workbook** / **Dữ liệu Excel** button expands or collapses them.

## Packing engine

`CartonFitEngine.evaluate()` tests all six axis-aligned FG orientations:

1. L × W × H
2. L × H × W
3. W × L × H
4. W × H × L
5. H × L × W
6. H × W × L

For every orientation it calculates the integer quantities along carton length, width, and height, then multiplies them to obtain physical capacity. The highest-capacity orientation is selected.

A carton passes only when physical capacity is at least the target quantity. Volume utilization is used for comparison and ranking only. A volume-only fit must never pass.

Existing cartons are ranked by:

1. Smallest non-negative capacity surplus.
2. Highest volume utilization.
3. Active lifecycle before other lifecycle values.
4. Smallest carton volume.

The engine returns and displays the Top 10 passing existing cartons. The highlighted current assignment is shown separately before those alternatives, using either the Weekly BOM source-of-truth label or an explicit workbook-fallback label.

## New-carton generation

`NewCartonGenerator` creates controlled candidates rather than searching millimetre by millimetre.

Packing patterns:

- `1 × 1 × targetQty`
- `1 × 2 × ceil(targetQty / 2)`
- `2 × 2 × ceil(targetQty / 4)`
- `2 × 3 × ceil(targetQty / 6)`
- `2 × 2 × 2`
- `3 × 2 × 2`
- `4 × 3 × 1`

Every pattern is applied to all six orientations. The generator adds 5 mm internal clearance to every proposed dimension, rounds upward to a 5 mm increment, removes duplicates, and tests retained candidates with the same physical fit engine.

The generator returns the Top 10 scored new-carton proposals. Every retained proposal must physically fit the selected FG target; volume alone cannot qualify a proposal.

For ordinary existing-FG proposals, shared-carton compatibility remains the primary ranking goal. For manual NPI input, `prioritizeDensity: true` makes selected-FG utilization and small carton volume the first priorities while still calculating how many workbook FG codes each proposal supports.

## 3D visualizer

`PackingVisualizer3D` uses embedded SVG polygons; it does not use WebGL or an external 3D library.

The view shows:

- A master-carton wireframe.
- Packed FG cuboids in the calculated `qtyLength × qtyWidth × qtyHeight` arrangement.
- Only the target quantity as solid boxes.
- Unused capacity positions as optional ghost outlines.
- Axis labels and packing statistics.

### Rotation and grab interaction

Rotation changes only the camera projection basis. Users can drag horizontally to change azimuth and vertically to change elevation with a mouse, pen, or touch pointer. The left/right buttons remain available for 15-degree steps:

```text
screenX = cos(angle) × x − sin(angle) × y
screenY = sin(elevation) × (sin(angle) × x + cos(angle) × y) − cos(elevation) × z
```

The carton, FG, orientation, and arrangement dimensions are never modified by rotation. Drag state stores only camera azimuth/elevation. The button view rotates in 15-degree steps and wraps after 24 steps. Reset returns both azimuth and elevation to the default isometric view.

Do not reintroduce rotation by swapping or decrementing `carton.width`, `carton.depth`, `fit.length`, or `fit.width`.

## Localization and theme

All maintained UI strings are stored in `I18n.text.en` and `I18n.text.vi`.

When adding or changing visible UI text:

1. Add the same key to both language dictionaries.
2. Use `data-i18n="key"` for static markup.
3. Use `this.t('key')` in `UiController` or `I18n.t('key')` elsewhere for generated content.
4. Re-render dynamic results after a language change.

Dark mode is implemented with CSS custom properties under `html[data-theme="dark"]`. New colors should use existing variables such as `--bg`, `--panel`, `--input`, `--ink`, `--muted`, `--line`, and `--soft` rather than fixed light-only colors.

## Known constraints

- Automatic sibling-workbook access requires the `.cmd` launcher because normal `file:///` pages cannot silently read adjacent files under standard browser security rules.
- The embedded reader supports `.xlsx` and `.xlsm`, not legacy binary `.xls`.
- Formula cells rely on cached values stored in the workbook.
- Proposal generation is synchronous and can take noticeable time with very large FG datasets.
- Physical sample validation remains mandatory. The tool does not account for corrugated-board thickness, compression, tolerances beyond configured clearance, inserts, bag deformation, weight, stacking strength, or shipping regulations.
- No result should be described as production-approved.

## Safe continuation checklist

Before handing off a future version:

1. Keep the application offline and self-contained.
2. Do not add external CDN, API, font, analytics, or library requests.
3. Preserve IDs as strings.
4. Preserve all six orientation tests.
5. Preserve physical-capacity gating; never use volume alone to pass a carton.
6. Test both manual NPI and existing-FG workflows.
7. For an existing FG, confirm the displayed assigned Master Carton ID comes from the newest Weekly BOM; treat `FG_MasterCarton.MasterCarton_ID` only as a comparison.
8. Confirm the FG and carton dimension badges accurately reflect matches in their respective dimension sheets.
9. Confirm the initial existing-FG 3D view uses the assigned carton when its dimensions are available.
10. Test both existing-carton and new-proposal 3D views.
11. Rotate left and right repeatedly and confirm displayed dimensions never change.
12. Test EN/VI switching after results are displayed.
13. Test dark mode with tables, inputs, linkage cards, proposal banners, and SVG wireframes.
14. Launch through the `.cmd` and confirm the newest adjacent workbook auto-loads.
15. Check the browser console for uncaught errors.
